GitHub OIDC authentication, IAM deployment permissions, ECR image
repositories, and CI jobs that build and push backend/chat images
without long-lived AWS credentials.

\vspace{0.5em}\noindent\textbf{Technical Implementation}\par

The CI/CD path uses GitHub Actions OIDC to assume the AWS deployment
role instead of storing long-lived AWS access keys. ECR image URIs are
based on AWS account, region, repository name, and immutable Git SHA
tags.

\{\{\textless{} mermaid \textgreater\}\} graph LR GitHub{[}``GitHub
Actions''{]} --\textgreater{} OIDC{[}``GitHub OIDC token''{]} OIDC
--\textgreater{} IAM{[}``IAM role: internship-github-deploy''{]} IAM
--\textgreater{} ECR{[}``Amazon ECR''{]} IAM --\textgreater{}
EKS{[}``Amazon EKS''{]} ECR --\textgreater{}
BackendImage{[}``internship-backend:\textless github.sha\textgreater{}''{]}
ECR --\textgreater{}
ChatImage{[}``internship-chat:\textless github.sha\textgreater{}''{]}
EKS --\textgreater{} Deploy{[}``scripts/k8s/deploy-eks.sh''{]}
\{\{\textless{} /mermaid \textgreater\}\}

The source repository includes deployment scripts for both EKS
application deployment and frontend deployment. I keep sensitive runtime
values such as \texttt{DATABASE\_\allowbreak{}URL}, \texttt{REDIS\_\allowbreak{}URL}, and
\texttt{SECRET\_\allowbreak{}KEY} in environment variables or Kubernetes Secrets, not
in published documentation.

\vspace{0.5em}\noindent\textbf{Weekly Results}\par

The project gained a cloud deployment identity model and image delivery
foundation. GitHub Actions can be used as the deployment controller, ECR
stores immutable image tags, and deployment scripts were prepared for
EKS rollout.

\vspace{0.5em}\noindent\textbf{Lessons Learned}\par

AWS CI/CD work depends on both IAM and runtime evidence. A workflow file
can be correct structurally, but I only mark authentication, image push,
or cluster access as verified when the corresponding AWS/Actions log is
available.
